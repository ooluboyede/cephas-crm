## Design changes
The protected registry is a candidate alternative to HMAC; not yet an accepted ADR. Issuer and runtime logins distinct. Issuance checks live idle-in-transaction target backend, DB, login and low 32-bit backend XID; verifier independently matches full xid8, PID, backend start, boot time, epoch, login, membership revision and expiry. Unique key excludes epoch so rotation cannot allow same live transaction to change scope. Issuer owner is NOLOGIN with narrowly used pg_read_all_stats membership; runtime has no such membership, protected table or issuer function grants. Live-target validation is NOT proof of end-to-end actor-to-connection association: an authorized issuer can still submit a foreign live tuple. Production trusted broker must own the socket/lease and derive tuple internally, bind actor credential and session, prevent arbitrary raw target selection, and withstand races; that broker is not implemented here. Full XID epoch guessing by trusted issuer, shared-login side channels (notification channels, signalling, catalog/planner/statistics, errors, timing), and denial-of-service require separate assessment; row isolation is not full noninterference.

## Session hygiene and restart
A held cursor can retain prior authorised results across commit, and arbitrary SQL can leave session state. The test harness explicitly performs ROLLBACK then DISCARD ALL before simulated actor switch and verifies cursor/prepared statement removal. Failed reset must destroy connection; no production pool implemented, no claim of end-to-end cancellation safety. Prepared statement reuse is separately tested to re-evaluate scope. Restart test persists database container state and checks prior bindings unusable and new authorised bindings valid. Full backup restore, concurrent issuer/database rollback, epoch custody, cancellation, long-running queries and cursor in-flight revocation remain open. Registry retention and transaction ID wraparound lifecycle require review. No assertion of hard expiry interruption; statement-based expiry and already materialised results are documented limitations.

## Gate 0.1.9.2 — Broker experiment
Parent 80dc1626fe55a3406963e250ae3eec927798b753; verified Run #11 (45955998900): 19/19, 35.500s, merge SHA 3444144b411963477063a0adf250c08c1758ad55, PostgreSQL 18.7 pinned digest unchanged. New suite expects 26 tests; previous count above is historical. Separate proof logins per tenant/BU provide database-enforced scope restriction in addition to registry binding. Legacy shared role exists only for regression tests; not used by broker. Broker authenticates disposable random bearer credentials, selects a fixed allowlisted operation and scope login, opens a fresh connection, obtains PID/full XID internally, calls issuer via separate login and closes both connections on every outcome. No raw SQL, caller role/actor/PID/XID or connection parameter. This is a trusted-process prototype using psql, not real OIDC, network service, production pool or credential isolation from a compromised process. Issuer is still trusted and can submit a different live target in its authorised scope; scope-specific DB roles prevent foreign-scope target binding but not same-scope principal misuse. No cross-tenant noninterference claim: PostgreSQL LISTEN/NOTIFY, signalling, locks, timing, catalog/error paths and colluding clients are residual threats; if strict isolation including covert channels is required, use separately evaluated database/cluster isolation. Full restore, cancellation, production credential management, broker API authentication and policy enforcement remain open. No reviewer acceptance requested.
