# CEPHAS CRM — Gate 0.1.8 Security remediation and disposable boundary proof
Status: Proposed proof specification, not implementation, acceptance or proof authorisation.
Parent: fc07a842f7421b056b11b365867fd1ba53737ef0. Scope: original Gate 0.1 acceptance; C-01/C-09 critical blockers, D01/D02, S01–S07.

## R01 — Reconciled requirements
This change aligns the reference architecture, ADR-0002, ADR-0005, licence baseline and Gate 0.1.5 sequence: ENABLE and FORCE RLS on protected tenant/BU data tables; authority data separately restricted; authenticated transaction-bound context; single BU by default; no silent licence grace; non-destructive audited recovery. Approval of these proposed changes remains pending. Original Gate 0.1 acceptance criteria are unchanged. Proof is proposed inside Gate 0.1, not as an implicit waiver permitting product implementation.

## R02 — Narrow proof scope and authorisation
Proposed Gate 0.1.9 disposable experiment only: isolated PostgreSQL 18 test instance; two tenants, two BUs each; synthetic principals, authority rows and overlapping record IDs; separate issuer/test harness, ordinary runtime login, protected owner roles; no product domain schema, external integrations, customer data, production keys, deployment or merge. Use ephemeral randomly generated test keys, disposable network/database and reproducible pinned tooling. No production migration. Record named engineering authority, approved SHA/scope, expiry and teardown obligation before execution. Approval pending. Stop on any cross-scope access, verification uncertainty or inability to reproduce.
Threat: arbitrary SQL under ordinary runtime credentials including SET, RESET, role switching, prepared statements, savepoints, cursors, transaction changes and catalog inspection; trusted issuer, database engine, owner/host and IdP compromise excluded. Isolation claim concerns foreign tenant/BU row data and mutations; resource consumption, timing/catalog side channels and same-scope misuse are residuals requiring review, not a proof of complete noninterference.

## R03 — Candidate capability design and failure rules
Use separate issuer authority with distinct credential and protected key. Issuer authenticates synthetic actor via test-only independent channel and authorises scope against authoritative membership; caller cannot pass arbitrary actor ID as proof of identity. Proof must exercise denied issuer calls, not merely generate valid tokens in the same untrusted runtime. Bind capability to deployment epoch, current full transaction ID, backend PID, backend start identity, session login role, principal, tenant, BU, membership revision, operation class, issued/expiry seconds, unique token ID and key ID. Use a strict versioned fixed-order ASCII encoding with bounded canonical lowercase UUID and integer fields, no separators in identifiers, explicit domain prefix, reject extra/missing fields, ambiguous integers and malformed encoding; proposed HMAC-SHA-256 over exact bytes, no algorithm negotiation. Exact byte grammar and independently checked constant-time comparison remain pre-code review items; no ad hoc crypto. If a reviewed constant-time database comparison cannot be demonstrated, redesign verification (e.g. reviewed asymmetric extension) rather than claiming secure HMAC.
Runtime GUC can be changed freely; verifier trusts only authenticated claims. Protect key/authority tables and functions using dedicated NOLOGIN owners, minimal grants, fixed trusted search_path, fully qualified identifiers and no dynamic SQL. Verify session_user rather than SECURITY DEFINER current_user. Check active membership revision under defined transaction snapshot rules, exact scope and current expiry. Prevent multiple valid capabilities for different scopes in one transaction using an issuer-side durable unique binding; reserve before signing, no reissue to different scope, fail closed on issuer state uncertainty. Tokens must not remain valid after restart/restore/failover; rotate epoch/key before enabling restored DB. Restore of issuer and database together is a separate rollback threat requiring protected external state; proof must not claim resistance until exercised.
Proposed proof expiry 30 seconds; statement/transaction duration and revocation semantics require tests. READ COMMITTED only; arbitrary SQL can request stronger isolation or retain cursors, so explicitly test and enforce or reject unsupported isolation/transaction modes at trusted verification boundary. Revocation is effective for fresh authorised operations/snapshots; do not promise interrupting an already materialised result. Bound in-flight work and test held cursors and pooled sessions. Same-role arbitrary SQL can alter timeout settings; do not assume those settings form an enforcement boundary. Record limitation or redesign if test demonstrates unbounded access after expiry/revocation.

## R04 — Proof implementation deliverables
Proposed isolated proof directory: README and scope manifest; pinned DB/tool dependencies; role/schema bootstrap SQL; issuer and verifier candidate; RLS and scoped composite FKs; synthetic fixtures; automated positive/negative tests; teardown and evidence manifest. Include direct connection tests as runtime login, separate privileged fixture setup, two concurrent sessions and real pool reuse. No fake DB, skipped tests, reliance solely on ORM predicates or static AST analysis. Preflight locally before one consolidated push, then CI against exact reviewed SHA. Do not commit secrets or unredacted tokens.
