# CEPHAS CRM — Gate 0.1.5 Tenant, identity and security boundary
Status: Proposed design; not implementation approval or independent acceptance.
Baseline: d5e43bfe6e0587b8b545dece398879454921ea63 (PR #1). Traceability: ADR-0002/0003/0004; Gate 0.1.3 A02–A04; Gate 0.1.4 D01/D02/D05 and TM-01–06/TM-14.

## S01 — Threat scope and security invariants
Protect against untrusted selectors, missing ORM filters, compromised tenant accounts, stale pooling and worker state, and arbitrary SQL execution under a normal runtime role insofar as tenant/BU isolation is concerned. The latter is a proposed stronger requirement than trusting mutable settings. An attacker with arbitrary SQL can still misuse grants within the authenticated scope; application operation permissions must not be described as database-enforced unless separately proven. Full compromise of the API process, trusted context issuer, DB superuser, migration owner, customer host or IdP is outside this isolation claim. No hidden CEPHAS support access. An installation that cannot satisfy the shared-schema proof must not enable shared multi-tenancy; separately reviewed isolated deployments may be considered.

## S02 — Identity and authority
Use customer-controlled OIDC provider; no in-house password authentication for initial profile. Validate configured issuer, audience, signature, algorithm, expiration and other protocol claims; use authorization code + PKCE, state and nonce as appropriate, exact redirect URI allowlist, TLS and secure server-side sessions. Map identity by immutable (issuer, subject), not email. Privileged roles require verified MFA and step-up according to a configured assurance mapping; never accept client MFA assertions. Server independently checks active tenant, BU, principal, membership and permission; selectors are requests, not authority. Reject missing/ambiguous scope. Default single BU per transaction, including tenant administrators; no null or wildcard scope. Tenant-wide reporting and shared tenant-level records are deferred until separately modelled and tested. Machine identities are explicit and distinct from human actors. No runtime self-grant or direct updates to authority records; membership administration uses a separate constrained audited management path with no self-escalation. Membership revocation applies to subsequent authorization statements/transactions; already authorised in-flight work needs an explicit bounded duration and revocation race policy. Fail closed if identity/membership verification is unavailable. Provider selection, JWKS rotation/outage policy and session/assurance limits remain design blockers.

## S03 — Authenticated transaction-bound context (proposed feasibility design)
Do not trust a plain SET LOCAL tenant ID, a setter callable with arbitrary IDs, a temporary table, application-only AST checks, or a GUC write restriction alone. Treat any runtime-controlled context carrier as untrusted.
1. API obtains verified server session and checks requested action. Start a single explicit READ COMMITTED transaction on a pinned connection; obtain DB deployment identity, current full transaction ID and backend identity. No protected data query before context is verified.
2. Separate customer-controlled context issuer independently authenticates the actor/service credential and checks live authoritative membership, requested scope and operation. A runtime SQL session cannot access issuer signing keys or invoke issuer with arbitrary principal assertions. Issuer authenticated service interface must not accept raw user IDs as authentication.
3. Issue a short-lived, versioned authenticated capability containing key ID, audience/deployment, runtime login role, transaction ID, backend identity, principal ID, tenant ID, BU ID, membership revision, operation class, issued-at/expiry and unique token ID. Bind to a fresh transaction and database instance/epoch; define replay protection across restart, restore and failover. Use an unambiguous bounded canonical encoding with no duplicate fields or algorithm negotiation. Proposed mechanism: HMAC-SHA-256 with a deployment-local symmetric context key, distinct from CEPHAS offline licence keys and release keys. Key available only to issuer and protected database verifier. Prefer reviewed cryptographic implementation; PostgreSQL pgcrypto feasibility and constant-time comparison must be established. No production key stored in source.
4. Runtime places capability in transaction-local carrier; RLS consumes only a trusted verifier result, never unsigned claims. Verifier checks integrity, exact binding, expiry against statement/current wall time (not frozen transaction start), audience, approved key, active membership revision and scope against protected authority records. Invalid/missing/oversized capability denies access; malformed parsing must not leak data. No fallback to unverified context. Changing carrier to different scope, replay across sessions/transactions and direct SQL attempts to read/modify verification keys must fail. Issuer must ensure one authorized scope per transaction; prove binding or use an independently reviewed immutable registry. Token exposure must not expand scope; redact from SQL logs/traces and error responses.
5. Use narrowly scoped SECURITY DEFINER verifier only if needed, owned by dedicated NOLOGIN role, fully qualified object references, fixed trusted search_path including pg_temp last, no dynamic SQL, no public EXECUTE or CREATE privileges, no generic signing or secret-reading function exposed. Explicit allowlisted EXECUTE grants. Prove no indirect key leakage through error, timing, views, ownership, roles or extension functions. No policy marked leakproof without justification. Evaluate RLS recursion, planner behavior, cache/stability and per-statement membership checks; never cache verification across authorization changes.
6. Commit/rollback in finally; on cancellation, connection invalidation, failed cleanup or uncertain state discard connection. No session-level defaults, autocommit protected queries, scope switching or transaction reuse. Initial pool profile session pooling with explicit transaction pinning; transaction poolers only after tests. Read replica, prepared statements, savepoints and retries must be reviewed; new transaction requires new capability.

This is a design hypothesis, not a proven mechanism. The original Gate 0.1 acceptance plan requires demonstrable isolation before closure. The proposed next step is a separately authorised minimal disposable PostgreSQL proof within Gate 0.1, not Gate 0.2 product implementation. See Gate 0.1.8 for scope and acceptance. Resolve capability encoding, key rotation, protected storage/role ACLs, issuer bootstrap and transaction-binding feasibility before feature expansion. If verifier cannot withstand same-role arbitrary SQL, block acceptance and redesign; do not silently downgrade.

## S04 — Data ownership and RLS rules
Classify every table as global read-only reference, protected authority metadata, or tenant/BU-owned. Deny unclassified tables to runtime. For initial BU-owned tables require NOT NULL tenant_id and bu_id, primary/unique keys scoped by tenant/BU and composite foreign keys (tenant_id, bu_id, object_id); business-unit membership refers to same tenant. Prevent ownership-changing updates via grants and explicit checks. Do not use global uniqueness for customer-supplied identifiers where it leaks existence; sanitize constraint errors. Tenant-level configuration and identity bootstrap use dedicated scoped functions, not a null-BU wildcard. Document ownership and policy inventory per migration.
For each protected table ENABLE and FORCE RLS, explicit SELECT/INSERT/UPDATE/DELETE policies with USING and/or WITH CHECK matching verified scope and applicable permissions. Default deny, no permissive broad policy or PUBLIC grants. Use restrictive policy composition where required and test combined policy semantics. Review partitions, views (security invoker where supported), functions, materialized views, triggers, foreign tables, sequences, COPY, TRUNCATE, REFERENCES, unique/FK side channels and cross-module access; deny unsupported paths. No direct tenant access via owner views or privileged reporting. RLS is not a substitute for resource/action authorization.

## S05 — Database roles
- crm_schema_owner: NOLOGIN; owns application schemas/tables; separate controlled migration identity may assume only for deployment.
- crm_runtime_api and crm_runtime_worker: distinct LOGIN roles, NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB NOREPLICATION, no ownership or memberships enabling SET ROLE to privileged roles, no DDL/extension management, no TRUNCATE or unrestricted functions. Grant only required table columns/operations and vetted verifier execution.
- crm_context_owner: NOLOGIN; owns protected context key storage/verifier; no application data bypass or runtime role membership. Key provisioning/rotation via separately authorized customer operator.
- crm_authority_owner and constrained membership-management interface: protect identity and membership records; no runtime direct grants, no self-escalation, audit changes.
- Backup/restore operator and emergency roles: separate credentials; not reachable from runtime, isolated and audited. Emergency support disabled by default, scoped customer approval, two-person approval, expiry and audit required before enablement.
Revoke unnecessary PUBLIC database/schema/function privileges; secure default privileges and trusted schemas. Check effective role inheritance, owner paths and catalog-visible secrets, not just role flags. Runtime secrets distinct from migration/backup credentials; no production secrets in CI.

## S06 — Asynchronous and nonrelational paths
Do not enable Celery/Redis until scope-safe worker proof passes. Queue envelope signed/authenticated by separate service key binds job ID, deployment, actor/service, tenant/BU, intended operation, parameter digest, issuance/expiry and replay policy. No database transaction capability in queued payload. Worker validates envelope, rechecks live authority/licence, obtains its own fresh transaction capability and enforces idempotency using scoped durable state. Retry/revocation and side-effect publication require reauthorization; external effects need idempotency/outbox design. Search/cache/export/object storage namespaces include tenant/BU and relevant permissions, reauthorize before download/publish, no global keys or public URLs. Defer cross-BU analytics. Queue broker credentials are not user identity.

## S07 — Required acceptance evidence (not executed)
Use real PostgreSQL under ordinary API and worker roles, two tenants each with at least two BUs and overlapping logical object IDs. Include authorised positive controls; assert no unauthorized reads, writes, side effects or existence disclosures; use exact SHA and retain redacted test output.
| ID | Adversarial test | Expected |
|---|---|---|
| B01 | missing/empty/malformed context or untrusted selectors | deny |
| B02 | valid tenant A/BU1 read/write/joins/upsert/delete versus tenant B | deny foreign rows and mutations |
| B03 | sibling BU, null/wildcard scope, ownership change and composite FK mismatch | deny |
| B04 | direct SQL SET/RESET carrier, forged capability, changed scope/actor/expiry/role, arbitrary setter calls | deny unverified context |
| B05 | replay token in another transaction/backend/deployment/epoch, rollback/savepoint/retry | deny; fresh context required |
| B06 | same pooled connection after commit/rollback/exception/cancellation; concurrent requests | no context leak |
| B07 | runtime SET ROLE, owner/DDL/TRUNCATE, protected key/authority read/write, function/search_path abuse | deny |
| B08 | wrong IdP issuer/audience/signature, expired tokens, revoked membership, missing privileged MFA | deny |
| B09 | scope change during request, membership revocation race, authority outage | documented bounded semantics; no new unauthorized operation |
| B10 | table without policies, view/partition/trigger/foreign table bypass, constraint error disclosure | fail coverage check or deny |
| B11 | forged/stale/replayed/revoked queue jobs, wrong worker role, retries | deny or idempotent authorized result |
| B12 | export/cache/search/object URL substitution, revoked download | deny |
| B13 | key rotation, unknown key, issuer/verifier outage, restore/failover and epoch collision | deny unsafe state |
| B14 | authorized scoped CRUD and valid membership lifecycle | succeed without widening scope |
Require migration inventory/catalog assertions, integration tests and independent review of actual verifier trust boundary; static AST scanning is supplemental only. Verify application action permissions separately. Record exceptions, residual risk, owner, expiry and approval. No test results claimed here.

## Closure decisions and next gate
Proposed S01–S07 require review and reconciliation with existing ADRs. D01/D02/D05 not closed: capability proof, exact crypto/encoding/rotation, IdP profile/revocation timing, authority administration, worker envelope/replay and compatibility remain open. Gate 0.1.6 must lock supported versions and specify enforceable CI evidence and document coverage. Remaining licence/audit/DR architecture decisions must also be resolved before independent architecture acceptance. Gate 0.2 implementation requires formal architecture approval and prior disposable boundary proof acceptance, unless an explicitly approved limited exception changes proof timing without authorising CRM features. Production release requires independently reviewed implementation and real adversarial evidence.
