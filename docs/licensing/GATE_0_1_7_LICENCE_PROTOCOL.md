# CEPHAS CRM — Proposed offline licence protocol v1
Status: architecture proposal; no production keys, implementation or approval.
Baseline: 04d8366e1ca44c8231dff54f98dd39d8379179be. Extends ADR-0005 and OFFLINE_LICENSING.md; unresolved contradictions require approval, not silent replacement.

## L01 — Envelope and encoding
JSON UTF-8 envelope with exactly payload and signature fields. Payload object contains exactly schema_version (integer 1), licence_id, product ("CEPHAS_CRM"), customer_id, tenant_id, deployment_id, environment ("production", "test" or "development"), edition, modules, limits, issued_at, not_before, expires_at, kid, alg ("Ed25519"). IDs use canonical lowercase UUID strings except kid, edition and module identifiers, which are case-sensitive ASCII identifiers from a reviewed registry. Modules are sorted unique ASCII identifiers; limits is a closed object containing max_users, max_records, max_transactions_per_day as nonnegative safe integers; zero means zero, never unlimited. Unlimited entitlement requires a separately versioned explicit representation. Define counted users as active licensed human accounts; count records and transactions per documented module inventory and UTC day. No unknown keys, duplicates, nulls, floats, invalid UTF-8, BOM, or unsupported schema. Times are integer UTC Unix seconds within an approved bounded range; issued_at <= not_before < expires_at. Contract issuance sets annual end date; verifier enforces signed dates, not an assumed 365-day year. Limit input to 64 KiB and bounded nesting/arrays; validate before canonicalisation. Use RFC 8785 JCS over validated payload with restricted ASCII strings and safe integers. Sign domain prefix ASCII "CEPHAS-CRM-LICENCE-V1" followed by one NUL byte and canonical UTF-8 bytes; signature is canonical unpadded base64url of exactly 64 bytes. Verify using a vetted Ed25519 library, not a custom primitive; pin library and test compatibility before use.

## L02 — Trust and validation
Pin separate offline trust-root public keys in verified release. A signed versioned trust bundle identifies product, monotonic sequence, validity interval, authorised licence signing key IDs and 32-byte public keys, activation/retirement windows and revocation entries. Use distinct domain prefix for trust bundle and distinct keys for licence, release and context issuance. Validate trust bundle signature and sequence before use; deny unknown, revoked or retired signing keys; key validity at issuance and verification must be explicitly supported by rotation overlap. No network fetch or fallback to untrusted key. Verify canonical envelope, signature, product, customer/tenant/deployment/environment, time, registered edition/modules and limits. Compare binding with provisioned trusted installation state, never a request field. Protected actions check entitlement server-side; seat/record/daily transaction enforcement uses transactional concurrency-safe reservations and idempotency. Do not log signature, keys or full licence. Error codes separate operator diagnostics from external response. No silent downgrade or grace.

## L03 — Renewal, revocation and recovery
Customer receives signed renewal before expiry; import atomically after validation. No mandatory CEPHAS connection; signed revocation/rotation updates delivered by authorised offline channel, not instantaneous. Protect highest accepted trust-bundle sequence and observed time outside ordinary database restore where feasible, with customer-controlled protected state; ordinary filesystem/DB timestamp alone does not resist privileged rollback. On missing, corrupt, backward or suspicious clock/state, deny protected writes and entitlement-dependent operations; retain data, permit only separately authenticated/audited recovery and customer-owned export path with normal tenant isolation. No destructive lockout. Recovery requires approved signed rebind/recovery package bound to old/new deployment, nonce, sequence and validity; root rotation via independently verified release/ceremony. Customer root/DB administrator controlling binary, trust state and clocks remains residual risk. Durable anti-rollback mechanism, tolerance, trusted time, key ceremony, exact trust bundle/recovery schemas and offline update logistics still require decision and proof.
